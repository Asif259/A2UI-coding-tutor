# AI Development Rules & Coding Guidelines — A2UI Tutor

> Rules for anyone (human or AI assistant) working on this codebase.  
> These are the ground rules established during development. Violating them will cause regressions.

---

## General Principles

1. **The catalog is truth.** If it's not in `agent/app/catalog/schemas.py` (and therefore `tutor_catalog.json`), it doesn't exist. Never add ad-hoc component handling outside the catalog flow.

2. **The host owns surface IDs.** The LLM must never see or set `surfaceId`. The server increments `Session.counter` and injects it. Client actions referencing unknown `surfaceId`s should be logged, not trusted.

3. **Actions describe, never trust.** When a student interacts with a surface, the payload tells you *what they did*, not *whether they were right*. Resolve correctness server-side from the stored surface snapshot.

4. **One repair, then fall back.** Invalid A2UI output gets exactly one retry with a corrected system prompt. Two failures = plain text rendered as a bubble. Do not loop indefinitely.

5. **Providers are secret on the server only.** The API endpoint that lists providers MUST mask the key (`apiKeyHint`). Never echo the full key back to the client.

## Python / Agent Rules

### Code Style
- Use **ruff** for linting and formatting. Run `ruff check . && ruff format .` before committing.
- Type annotate all public functions. Omit annotation only for trivial getters.
- Keep modules under 300 lines. Split when exceeded.

### Error Handling
- Wrap every LLM call in `try/except` with specific handling for:
  - `AuthenticationError` → log, skip provider, try next
  - `RateLimitError` → record cooldown timestamp, try next
  - `TimeoutError` → return error bubble to client
  - Any other exception → log traceback, return plain-text fallback
- Never let an unhandled exception escape a route handler (FastAPI catches it, but loses context).

### Prompt Engineering
- The `ROLE` constant in `tutor.py` is the system prompt. Edit it carefully — it governs agent behavior.
- Never concatenate unsanitized user input into the system prompt. Use structured message lists.
- Keep CATALOG_INSTRUCTIONS near the top of the system prompt so the model sees component constraints early.

### Tests
- Mock the LLM client in all unit tests (`unittest.mock.AsyncMock`). Never hit a real model in CI.
- Keep route and provider tests hermetic: mock HTTP with `httpx.MockTransport`; no network in CI.
- Test names should say what behavior they protect (see `agent/tests/test_models.py`).

## TypeScript / Web Rules

### Code Style
- Strict TypeScript (`"strict": true` in `tsconfig.json`). No `any` without explicit comment justification.
- Match the existing style in `web/src`: 2-space indent, semicolons, double quotes, trailing commas where the file already uses them.
- Components live in `web/src/components/`; API helpers in `web/src/api.ts`.

### Catalog Sync
- Never edit `tutor_catalog.json` by hand. It is generated by `agent/app/catalog/build.py`.
- When adding a new component view in React, register it in `catalog/components.tsx` AND extend the schema in Python. Both must ship together.
- CI fails if the compiled catalog hash differs between Python and TypeScript consumers.

### Component Architecture
- Each A2UI component is a React function view in `web/src/catalog/components.tsx` that receives bound props and reads actions off `props` (the binder has already resolved them).
- Actions fired by the renderer are `{name, surfaceId, sourceComponentId, timestamp, context}`; `api.ts` adds the timestamp and empty context.
- Keep handlers small; extract side effects into named helpers when a view grows past a screen.

### State Management
- React state lives in `App.tsx`. Lift state only when two siblings need shared access.
- No Zustand, Redux, or Context unless a clear need emerges. The app is small enough for props drilling.

## Git & Workflow Rules

1. **Conventional commits.** Format: `feat(agent): add dark mode toggle` or `fix(tutor): repair loop on invalid json`. Types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.

2. **Branch from main.** Work on feature branches: `feature/course-browser`, `fix/gemini-timeout`.

3. **No secrets in git.** `.env`, `providers.json`, and any API keys must be in `.gitignore`. Use `.env.example` for documented variables.

4. **PRs require green CI.** All checks must pass: ruff, pytest, tsc, vitest, catalog-sync.

5. **Update tracker.md when shipping.** Every merged feature gets a checkbox tick and commit reference.

## Security Rules (Non-Negotiable)

| Rule | Why |
|------|-----|
| Bind to `127.0.0.1` only | Prevents accidental internet exposure |
| `providers.json` mode 0600 | Owner-read-only; denies sibling processes |
| Never log `api_key` value | Even in debug logs, mask or omit |
| Validate `base_url` regex | Prevent SSRF through malicious provider URLs |
| No client-side API key storage | Keys live only on the server |
| Treat the API as local-only | There is no login and no CSRF token; the network boundary is the security boundary |

## Performance Rules

1. **Load the catalog once.** Don't parse `tutor_catalog.json` on every request; it is loaded at import and reused.

2. **Stream large responses when possible.** For long surfaces, consider chunked rendering. Currently blocked by non-streaming LLM clients — plan for P1.

3. **Debounce send-button taps.** Client-side debounce of 300 ms prevents double-submit on slow networks.

4. **Profile before optimizing.** A2UI rendering is client-side fast; bottlenecks are almost always network or LLM latency, not DOM cost.

## Docs Maintenance Rules

1. **Docs live in `docs/`.** Not in `README.md` beyond a high-level overview. Long-form docs go to individual files.

2. **Cross-reference between docs.** Use relative links: `[PRD](PRD.md)`, `[TRD](TRD.md)`. Always verify links resolve.

3. **Update tracker.md alongside code changes.** A feature isn't "done" until the tracker row is checked off.

4. **Delete stale docs.** If a feature is removed, its docs section goes with it. Stale docs are worse than no docs.

---

## What to Ask Before Changing

Before editing any file, confirm:

1. Does this touch the catalog? → Check Python schema AND TypeScript view registration.
2. Does this change the LLM prompt? → Run `evals/run_eval.py` to check validity rate.
3. Does this add a new API endpoint? → Add OpenAPI-compatible tests.
4. Does this affect session state? → Check in-memory serialization and potential future SQLite migration.
5. Is this a breaking change? → Bump version, update CHANGELOG, notify in PR description.
